# ADR 004 — Hermes 2.0 contracts

**Status:** Accepted
**Date:** 2026-09-28
**Deciders:** Project lead
**Builds on:** [ADR 003](003-terminal-first-vendor-neutral.md) (terminal first, vendor-neutral; Hermes observes, never types)

## Context

Sixteen 2.0 features are built in parallel, by different people and agents, and most of them meet at the same few places: what a session's status is, what a session reports, where "waiting on you" items go, how a turn is named in git, and two files a repository can carry. If every feature invented its own shape at those places, the last one to merge would have to reconcile them all.

This ADR lands those shapes first, small and tested, with nothing behind them yet. Every later feature builds against them.

## Decision

The seams below are the contract. **Later features may only ADD to them**: a new status kind, a new event variant, a new optional field, a new inbox kind, a new file key. Nothing is renamed, removed or given a different meaning without a new ADR. Readers on both sides tolerate fields they do not know (the frontend parser drops them; the Rust types ignore them), so a newer producer never breaks an older reader.

Each seam lives in `src/agent/contract/` (TypeScript) and, where the backend takes part, in `src-tauri/src/contract/` (Rust). One fixture, `src/agent/contract/fixtures/session-events.json`, is read by the tests on both sides so the wire format cannot drift.

### 1. AgentStatus — `status.ts`, `contract/mod.rs`

One vocabulary for every agent, whatever it is and however it is observed:

`needs_approval`, `needs_answer`, `gate`, `check_failed`, `error`, `limited`, `plan_ready`, `done_unread`, `working`, `startup_prompt`, `starting`, `idle`, `exited`

Each status carries a **confidence** — `exact` (a nonce-verified hook or protocol event from the agent itself), `signal` (a notification any program could print), `guessed` (a PTY heuristic) — and a one-line **detail** for people (the command awaiting approval, the question, the reset time).

- **Owner:** F10 fills `deriveStatus` (signals → status, table-tested per kind) and the glyph-plus-word rendering. F11 produces the exact and signal sources. N19 fills `limited`; F27 fills `check_failed`; F28 fills `gate`.
- Everything that shows a status (F12 inbox, F08 chips, sidebar, title bar) consumes this type only, never a vendor's own words.
- **Filled by F10:** `src/agent/status/deriveStatus.ts` folds a session's events into the status it shows (exit wins; a report at least as certain replaces the current one; a source may correct itself; a less certain report only replaces `idle`, or an agent reported as ended in a terminal that is still open once something runs there again; the PTY's heuristics rank below any named guess; `done_unread` reads `idle` once a person has seen the session). `src/agent/status/attentionStore.ts` serves it per session and as a cross-session summary through `useSyncExternalStore`; `src/agent/status/presentation.ts` gives every kind a glyph and a word.

### 2. SessionEvent and the per-session store — `events.ts`, `sessionEventStore.ts`, `channel.ts`, `contract/mod.rs`

What a session reports, as a tagged union: `status`, `turn_start`, `turn_end`, `turn_failed`, `turn_interrupted`, `attention {detail}`, `identity {vendorSessionId, model, permissionMode}`, `exit {code, signal}`. Every event has `at` (epoch ms) and an optional `source` ("hook:claude", "osc", "pty", "plugin:<id>", "e2e").

Rust emits every event on **one** Tauri channel, `hermes:session-event`, as `{ sessionId, event }` (`contract::emit_session_event`). The frontend attaches one listener at boot (`main.tsx`) that parses each payload with `parseSessionEvent` and folds it into the store; a malformed payload is logged and dropped.

The store keeps one frozen snapshot per session — status, identity, turn counters, the last attention detail, the exit, the last 200 events — replaced only when an event lands, and readable with `useSyncExternalStore` through `useSessionEvents(sessionId)`. The store derives nothing except that an `exit` sets the status to `exited`, exactly: a process ending is a fact, not a guess.

- **Owner:** F11 emits the events (spool watcher, OSC, PTY heuristics) and the identity events that F08 renders. F20 consumes turn boundaries. F14 and F31 add usage events (an additive variant). N20 replays events on reattach. F36 exposes the normalised events to plugins.
- **Providers (F19):** `src/agent/providers/` holds the only code allowed to branch on an agent's id (lint rule `hermes-vendor/no-vendor-id-checks`). The `terminal` provider reports for every terminal session (PTY phase as `guessed` with source `pty`, the launch helper's startup states with source `hi`, identity with source `hermes`); the `agent-view` provider maps the optional Agent view into the same events (source `agent-view`, exact). A contract test runs one event script against every provider.
- **Added by F10 (additive):** `subscribeAllSessionEvents(listener)` on the store, told the session id after every event or clear, for stores that span sessions.
- **Test seam:** with `VITE_HERMES_E2E=1`, `window.__HERMES_E2E__.injectSessionEvent(sessionId, event)` feeds an event through the same parser, and the test build's `emit_session_event_for_test` command pushes one through the Rust side of the channel. `e2e/app/scenarios/C0-session-event-bridge.mjs` proves both on the real app, with a negative control on each side.

### 3. `hi signal` spool record — `signal.ts`, `contract/signal.rs`

The `hi signal` helper appends **one JSON line** per agent hook event to the session's spool file:

```
{"v":1,"ts":1790000000,"session":"<sid>","agent":"claude","nonce":"<nonce>","event":"PermissionRequest","payload":{...}}
```

The nonce is minted by Hermes per launch and handed to the agent's hook configuration. A record whose nonce does not match is never `exact`. Payloads are capped at 8 KB. `signalRecordToSessionEvent` / `to_session_event` map a record to an event through the status table of the signals report (prompt and tool events → `working`, permission → `needs_approval`, question → `needs_answer`, `ExitPlanMode` → `plan_ready`, turn end → `done_unread`, failure → `error`, session end → `exit`, `Notification` → `attention`).

- **Owner:** F11 ships the helper, the per-launch configuration for each agent and the spool watcher, and extends the table per agent. The record format itself is fixed here.

### 4. Turn ledger — `turns.ts`, `contract/turns.rs`, schema step 3

A `Turn` is `{ sessionId, n, ref, startedAt, endedAt, diffstat: { files, insertions, deletions } }`. Its snapshot lives in the hidden git reference **`refs/hermes/<session>/turn/<n>`**; the session id must be a valid ref component and `n` starts at 1. Schema step 3 adds the `agent_turns` table (additive, through the existing `user_version` ladder with its backup). The Tauri commands `list_turns` and `get_turn_diff` exist and answer with nothing (`[]`, `null`) until the ledger is filled.

- **Owner:** F20 writes the snapshots and the rows and fills the commands. F21 (Review Desk), F22 (Land sheet), F27 (check results stored on the turn) and F31 (diffstat as the universal work signal) read them.

### 5. Attention inbox — `inbox.ts`

An `InboxItem` is `{ id, kind, sessionId, detail, createdAt, source }` with `kind` one of `blocked`, `ready`, `gate`, `error`, `limit`. The store offers `raise`, `resolve`, `list` (oldest first — the order ⌘I visits them) and a subscription for React. Raising the same `(kind, sessionId, detail)` while it is open returns the open item. A plugin's `inbox.raise()` takes `{ kind, sessionId?, detail }` and the host stamps `source: "plugin:<id>"`; a plugin can never claim another source.

- **Owner:** F12 renders it (badge, listbox, ⌘I, notifications, sleep). F26 raises `error` on a failed setup, F27 raises `error` on `check_failed`, F28 raises `gate`, F31 and N19 raise `limit`, F36 exposes `raise()` to plugins.

### 6. Repository files — `worktreeToml.ts`, `featureFrontMatter.ts`

**`.hermes/worktree.toml`**: `setup = [...]`, `copy = [...]`, `done_when = [...]`, and a `[ports]` table of `name = number`. The reader understands the TOML subset the file needs and reports any other construct with its line number; unknown keys are kept in `ignored`.

**`.hermes/features/<slug>/feature.md`** starts with front matter: `slug` (a branch component), `track` (`Quick` | `Light` | `Full`), `phase` (`questions` … `implement`, `done`), `gate` (`none` | `waiting` | `approved`), `done_when` (a list). The reader returns the metadata and the body, or an error with its line number for the "feature.md can't be read (line n)" message.

- **Owner:** F26 runs the recipe (and refuses copy patterns that match tracked files). F27 runs `done_when`. F28 owns the feature folder, the watcher and the gates. F15 writes the first `feature.md` for a Full track.

## What this ADR does not do

No UI, no behaviour, no feature flag: nothing here is visible to a user, so nothing needs gating. The shapes are the deliverable.

## Consequences

- A feature that needs a new field adds it as optional, with a test in the shared fixture where the wire format is involved, and updates this ADR's list.
- A feature that needs a different shape writes a new ADR and a migration for anything already stored.
- The e2e injector is the way to put a session into any state in a real-app scenario without a real agent; scenarios for the features above should use it together with the fake agents.
